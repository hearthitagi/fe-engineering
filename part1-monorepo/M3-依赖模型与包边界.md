# M3 依赖模型与包边界

> **目标层级**：L2 ｜ **前置**：M2 ｜ **预计**：5h
> **本章产物**：依赖体检报告 + `docs/runbook.md` 的第一批条目

## 0. 先看终点

```powershell
PS> pnpm why react
react@19.x
└── @lab/admin@0.0.0 (dependencies)

Found 1 version of react

PS> pnpm --filter "@lab/admin..." list --depth -1
# 只列 admin、ui、utils 三个包（格式为 包名@版本 路径）

PS> pnpm --filter "...[HEAD~1]" list --depth -1
# 上次提交以来受影响的包及其依赖者
```

本章结束时，你要能解释：为什么 admin 里 `import 'lodash'` 会失败，而把 `nodeLinker` 改成 `hoisted` 后又能跑——这两种现象分别意味着什么。

## 1. 知识讲解

### 1.1 三层结构

```
全局 store（内容寻址，全机器共享）
   └─ ~/AppData/Local/pnpm/store/v11/files/...
项目 node_modules/
   ├─ .pnpm/                    # 每个包的真实位置，目录名带版本与哈希
   ├─ react -> .pnpm/react@19.x/node_modules/react
   └─ @lab/ui -> ../../packages/ui
每个包自己的 node_modules/
   └─ 只包含它在 package.json 里声明的依赖
```

关键在最后一层。`apps/admin/node_modules` 里只有 admin 声明过的包；`packages/ui/node_modules` 里只有 ui 声明过的包。**没有任何一层会把别人的依赖「提升」到你能看见的地方。**

所以 admin 想用 `lodash`，必须自己声明；靠 ui 装了 lodash 是拿不到的。

### 1.2 幽灵依赖是怎么来的

npm / yarn 经典模式把所有依赖尽量平铺到根 `node_modules`：

```
node_modules/
├─ lodash/          # 其实是 ui 的依赖
├─ react/
└─ ...
```

Node 解析模块时向上逐级找 `node_modules`，于是 admin 没声明 lodash 也能 `import 'lodash'`。本地能跑，CI 换个安装顺序或换个包管理器就崩——这就是幽灵依赖。

pnpm 的隔离结构从物理上杜绝了它。注意：**`strictPeerDependencies` 与幽灵依赖无关**，它管的是 peer 版本不满足时是否报错。网上很多文章把这两件事混为一谈。

### 1.3 想复现幽灵依赖，只有一种办法

在 `pnpm-workspace.yaml` 里加一行：

```yaml
nodeLinker: hoisted
```

pnpm 会退回平铺结构，幽灵依赖立刻出现。这个开关不是「兼容模式」，是「放弃隔离」。只在排查老项目时临时用，不要提交。

> pnpm 11 起，`.npmrc` 只读 registry 与认证；`node-linker=hoisted` 写在那里不会再生效，必须写成 `pnpm-workspace.yaml` 的 `nodeLinker`。

### 1.4 重复版本：单仓里最贵的错误

React 出现两份的典型路径：

- ui 把 React 写进 `dependencies`，版本 `^18.3.0`
- admin 用 React 19

结果：`pnpm why react` 显示 `Found 2 versions of react`，运行时 hooks 直接报 `Invalid hook call`。

规则：

| 包类型 | React 放哪 | 原因 |
|---|---|---|
| 应用 | `dependencies` | 应用自己运行 |
| 组件库 | `peerDependencies` + `devDependencies` | 由宿主提供，库只声明契约 |

同样的逻辑适用于任何「有单例要求」的库：`react-dom`、`styled-components`、状态库。

### 1.5 peer 依赖不满足时

pnpm 默认会自动安装满足范围的 peer，并在不满足时给警告。警告不是噪音：

```
WARN  Issues with peer dependencies found
└─ @lab/ui
   └─ ✕ unmet peer react@^19.0.0: found 18.3.1
```

看到这个就去查版本，不要用 `strictPeerDependencies: false` 关掉。

### 1.6 `--filter` 全语法

| 写法 | 选中范围 | 典型用途 |
|---|---|---|
| `--filter "@lab/admin"` | 只有 admin | 单包开发 |
| `--filter "@lab/admin..."` | admin 及其**依赖** | 构建 admin 前需要的一切 |
| `--filter "...@lab/admin"` | admin 及其**依赖者** | 改 admin 后要连带验证谁 |
| `--filter "...[HEAD~1]"` | 自上次提交以来改动的包 + 依赖者 | 增量 CI |
| `--filter "./packages/*"` | 按路径匹配 | 批量操作内部包 |
| `--filter "!@lab/h5"` | 排除 | 跳过不相关的包 |

记忆方法：**省略号在包名后面 = 往下（依赖），在前面 = 往上（依赖者）。**

### 1.7 拓扑序不是可选项

`pnpm -r run` 默认按依赖排序，`--parallel` 关闭排序。构建链路里，app 依赖 ui，ui 依赖 utils；并行构建时 app 可能拿到 ui 的旧产物甚至没有产物。

结论：**build / typecheck / test 用 `-r`，dev 用 `-r --parallel`。**

## 2. 实操

### 2.1 看清链接

```powershell
pnpm store path
Get-ChildItem node_modules/.pnpm | Select-Object -First 8 Name
Get-Item apps/admin/node_modules/@lab/ui | Select-Object LinkType, Target
```

预期：`LinkType` 是 `Junction` 或 `SymbolicLink`（Windows 视权限而定），`Target` 指向 `packages/ui`。这就是 `workspace:*` 的实际效果。

```powershell
pnpm why react
pnpm list -r --depth 0
```

`--depth 0` 只看直接依赖，用来确认每个包声明了什么。

### 2.2 亲手制造一次幽灵依赖

先给 ui 装一个 admin 没有声明的包：

```powershell
pnpm --filter "@lab/ui" add lodash
```

在 `apps/admin/src/App.tsx` 顶部加一行：

```tsx
import { debounce } from 'lodash'
```

并在按钮上用它：

```tsx
<Button onClick={debounce(() => alert('ok'), 300)}>点我</Button>
```

```powershell
pnpm dev:admin
```

预期：Vite 报 `Failed to resolve import "lodash"`。

现在改 `pnpm-workspace.yaml`，在文件末尾加一行：

```yaml
nodeLinker: hoisted
```

```powershell
pnpm install
pnpm dev:admin
```

预期：能跑了。**这就是幽灵依赖**：代码依赖了一个没有声明的包，只是安装结构恰好让它可见。切换 `nodeLinker` 会触发一次完整重装，耗时比平常长，属正常。

恢复：

```powershell
# 删掉 pnpm-workspace.yaml 里的 nodeLinker 行
pnpm install
pnpm --filter "@lab/ui" remove lodash
# 删掉 App.tsx 里的 lodash 引用
```

再启动一次，确认又报错。把这段现象记进 `docs/runbook.md`。

### 2.3 制造一次重复 React

```powershell
pnpm --filter "@lab/admin" add "react@^18.3.0" "react-dom@^18.3.0"
pnpm why react
```

预期：看到 18 与 19 两份，并有 peer 警告。`pnpm dev:admin` 后点按钮，控制台大概率出现 `Invalid hook call`。

恢复：把 `apps/admin/package.json` 里的 react、react-dom 改回 `"catalog:"`，执行 `pnpm install`，再 `pnpm why react` 确认只剩一份。

### 2.4 把 filter 用熟

```powershell
pnpm --filter "@lab/admin" list --depth -1
pnpm --filter "@lab/admin..." list --depth -1
pnpm --filter "...@lab/ui" list --depth -1
pnpm --filter "./packages/*" list --depth -1
pnpm --filter "!@lab/h5" list --depth -1
```

逐个对照 1.6 的表，确认选中的包与预期一致。再看改动筛选：

```powershell
git add -A
git commit -m "chore: m3 dependency lab"
pnpm --filter "...[HEAD~1]" list --depth -1
```

预期：只列本次改动涉及的包。这条命令会在 C4 的增量 CI 里原样出现。

### 2.5 观察拓扑序

```powershell
pnpm -r exec node -p "require('./package.json').name"
pnpm -r --parallel exec node -p "require('./package.json').name"
```

前者应稳定地从 utils 到 app；后者顺序不稳定。多跑几次，把两次输出记进报告。

### 2.6 写依赖体检报告

`docs/dependency-report.md`：

```md
## 依赖体检（M3）
- React 版本数：1（pnpm why react）
- 内部包引用方式：全部 workspace:*
- 未声明依赖：0（幽灵依赖演练后已清理）
- peer 警告：0
```

## 3. 排障

**3.1 filter 写错了，命令却成功**

pnpm 12 默认在没有任何包匹配时**静默退出 0**，不打印错误。CI 会以为任务跑过了。脚本里加 `--fail-if-no-match`，或先 `pnpm -r list --depth -1` 核对包名。

```powershell
pnpm --filter "@lab/admni" build --fail-if-no-match
# 预期：报错并以非 0 退出
```

**3.2 `ERR_PNPM_PEER_DEP_ISSUES`**

版本范围不满足。先 `pnpm why <pkg>` 找到是谁引入的，再决定升级还是放宽 peer 范围。不要直接关掉检查。

**3.3 `Invalid hook call`**

九成是两份 React。`pnpm why react` 确认，检查组件库是否把 React 写进了 `dependencies`。

**3.4 改了源码，应用没热更新**

`@lab/ui` 被 Vite 当成普通依赖预构建了。确认 `exports` 指向源码（M2 的配置），必要时重启 dev server 清掉 `node_modules/.vite`。

**3.5 `nodeLinker: hoisted` 忘了改回来**

症状：本地能跑、CI 报找不到模块。检查 `pnpm-workspace.yaml`，并在 CI 里加一条守卫：搜索仓库里是否存在 `nodeLinker`。

## 4. 故障演练：让 CI 和本地分叉

**制造**：在 `pnpm-workspace.yaml` 保留 `nodeLinker: hoisted`，提交并推送，观察 CI（第 8 周才有，先记下）。

**观察**：本地 `pnpm install` 后所有依赖平铺，未声明的 import 能跑；CI 从零安装也会平铺，但依赖 hoisting 顺序可能与本地不同，问题变得不可复现。

**修复**：删掉该行，重新安装，确认 `pnpm why` 与本地目录结构恢复隔离。

**沉淀**：`pnpm-workspace.yaml` 只放与依赖图、安装结构相关的明确配置；任何改变 `nodeLinker` 的改动必须走评审。

## 5. 闭卷练习：给陌生仓库做依赖体检

找一个公司的 pnpm 仓库（或把 `fe-lab` 复制一份），不看教程完成：

1. 列出重复版本最多的 5 个依赖，写清各自被谁引入
2. 找出 3 个「代码里 import 了但 package.json 没声明」的依赖
3. 用 `--filter "...[HEAD~1]"` 只跑受影响包的构建
4. 产出一页报告：重复版本、幽灵依赖风险、peer 警告、构建顺序

**过关标准**：报告里每条结论都附一条可复现命令，同事照抄能得到同样结果。

## 7. 自测

1. store、`.pnpm`、包内 `node_modules` 三者的关系是什么？
2. 幽灵依赖的物理成因是什么？为什么 pnpm 默认没有？
3. `strictPeerDependencies` 管什么？它和幽灵依赖有什么区别？
4. `--filter "a..."` 与 `--filter "...a"` 分别选中谁？
5. 用 3 句话解释「为什么构建不能用 `--parallel`」，要求举一个具体后果。

<details><summary>参考答案</summary>

1. store 存包内容；`.pnpm` 是项目内按版本组织的真实位置；包内 `node_modules` 只放自己声明的依赖，用链接指向 `.pnpm`。
2. 平铺安装把别人的依赖提升到上层，Node 向上查找就能看到。pnpm 不做平铺，每个包只能看到自己声明的依赖。
3. 管 peer 依赖版本是否满足；幽灵依赖是模块可见性问题，两者无关。
4. 前者是 a 及其依赖，后者是 a 及其依赖者。
5. 构建有依赖顺序：app 依赖 ui，ui 依赖 utils。并行时 app 可能在 ui 还没产出时就开跑，拿到旧产物或直接失败，且失败与否取决于机器速度，很难复现。

</details>
