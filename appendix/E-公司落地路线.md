# 附录 E · 公司落地路线

> **目标**：不依赖“公司同意大改造”，也能把本教程的能力用起来；先从只读审计和影子仓库开始，再逐级争取。
> **原则**：小步、可回滚、有数据、不打断发布。

## 0. 先看终点

90 天后，你希望拿到三样东西：

1. 一份公司项目的**现状基线**（构建耗时、产物体积、CI 时长、失败率）；
2. 一个**非阻塞**的检查（先在旁边跑，不挡合并）；
3. 一页能给主管看的**落地提案**（范围、收益、成本、风险、回滚）。

不是“把公司项目改成本教程的样子”。公司项目有历史、有发布窗口、有权限边界；你要做的是**在不破坏它的前提下证明价值**。

```mermaid
flowchart LR
  A[只读审计] --> B[影子仓库/个人实验]
  B --> C[非阻塞检查]
  C --> D[稳定后设为 required]
  D --> E[产物/镜像]
  E --> F[手动部署与回滚]
  F --> G[再评估 Monorepo/工具升级]
```

## 1. 先认清公司约束

| 约束 | 表现 | 应对 |
|---|---|---|
| 没有仓库管理员权限 | 不能改分支保护/CI 变量 | 先做本地/影子验证，再提提案 |
| 老项目依赖复杂 | 全量 lint/typecheck 一跑就红 | 先只检查改动文件或新代码 |
| 发布窗口固定 | 不能随时改流水线 | 先加旁路 job，不挡发布 |
| 使用 GitLab | 不是 GitHub Actions | 用附录 F 的对照实现 |
| 安全/合规 | 不能把代码/secret 传到个人环境 | 用脱敏样本；不复制 `.env`/token |
| 多团队共用 runner | 资源排队、缓存互相影响 | 先度量，再谈缓存/并发 |
| 历史包管理器 | npm/yarn 混用 | 不先换 pnpm；先统一锁文件与 CI |

### 1.1 不要做的第一件事

- 不要先格式化整个仓库；
- 不要先换包管理器；
- 不要先迁 Monorepo；
- 不要先上 Turborepo/Nx/K8s；
- 不要把“全量 lint”设成 required；
- 不要在没有回滚方案时动生产部署。

这些动作会把“工程化”变成“大爆炸”，通常活不过第一次发布。

### 1.2 你可以在个人环境练什么

| 练习 | 用公司代码？ | 做法 |
|---|---|---|
| pnpm workspace | 否 | 本教程 `fe-lab` |
| Vite 构建/分包/资源 | 否 | 自己的示例仓库 |
| CI 流水线 | 否 | GitHub 私有仓库 + 附录 F 的 GitLab 镜像 |
| Docker/NAS | 否 | 自家 NAS 或本地 Compose |
| 公司现状审计 | 只读 | 单独 clone，记录命令与输出，不改文件 |
| 非阻塞检查 | 经批准 | 只加旁路 job，不设 required |

只读审计也要注意：不要在公司的 clone 里随手 `pnpm install` 后提交 lockfile；用 `git status` 确认没有改动。

## 2. 五级落地阶梯

| 级别 | 动作 | 是否阻塞 | 需要的权限 | 产出 |
|---|---|---|---|---|
| L0 观察 | 记录构建/CI/发布现状 | 否 | 读代码 | 基线表 |
| L1 影子 | 个人仓库复刻关键脚本 | 否 | 无 | 可复现实验 |
| L2 旁路 | CI 加非阻塞 job | 否 | CI 配置 | 检查报告 |
| L3 门禁 | 稳定后设为 required | 是 | 分支保护 | 合并前拦截 |
| L4 交付 | 产物/镜像/手动部署 | 是（发布） | Registry/NAS | 可回滚发布 |

大多数人卡在 L2：能加 job，但不敢设 required。不要跳级；先在 L2 跑两周，收集误报率和耗时。

## 3. 30/60/90 天计划

### 第 1 个月：只读与基线

| 周 | 动作 | 产出 |
|---|---|---|
| 1 | 记录公司项目的 Node/包管理器/构建命令/CI 时长 | `company-baseline.md`（脱敏） |
| 2 | 在个人仓库复刻最小构建链路 | 可复现的 Vite/pnpm 实验 |
| 3 | 找 2 个真实失败案例（构建慢/发布旧版/回滚难） | 问题清单 |
| 4 | 写一页提案草稿，找一位技术负责人聊 | 反馈记录 |

基线至少包含：

```text
机器/runner：
Node/包管理器：
install 命令与耗时（3 次中位数）：
build 命令与耗时（3 次中位数）：
产物体积（raw/gzip）：
CI 总时长：
最近 10 次发布失败原因：
```

### 第 2 个月：非阻塞检查

| 周 | 动作 | 产出 |
|---|---|---|
| 5 | 在 CI 加 `build` 旁路 job（`allow_failure: true`） | 每次 MR 有构建结果 |
| 6 | 加 smoke/体积报告，只报告不拦 | 趋势数据 |
| 7 | 统计误报、耗时、维护成本 | 是否值得 required 的判断 |
| 8 | 与团队评审；选一个低风险检查设 required | 第一个门禁 |

建议第一个 required 检查选**最稳定、最快、误报最低**的，例如 `build` 或 `typecheck`；不要先选全量 lint。

### 第 3 个月：交付与回滚

| 周 | 动作 | 产出 |
|---|---|---|
| 9 | 产物 artifact 或镜像（按公司目标） | 可下载/可拉取 |
| 10 | 测试环境手动部署 | 部署记录 |
| 11 | 回滚演练 + 运行手册 | MTTR 数据 |
| 12 | 复盘，决定是否扩大范围 | 下一季度提案 |

如果公司没有容器/NAS 目标，就停在 artifact + 手动发布；不要为了“完整”硬上 Docker。

## 4. 不改公司项目怎么练

### 4.1 影子仓库

把公司的**目录结构、脚本名、关键依赖**脱敏后放进个人仓库：

```text
shadow-repo/
├─ package.json          # 只保留结构，不复制业务
├─ pnpm-workspace.yaml
├─ apps/web/             # 一个最小页面
├─ packages/ui/          # 一个共享组件
└─ tooling/checks/       # 从教程复制
```

不要复制：

- `.env`、token、内网地址；
- 真实业务数据/图片；
- 公司私有包（用公开替代或本地 mock）。

### 4.2 只读审计命令

```powershell
git clone <company-repo> company-audit
cd company-audit
git status

# 只读观察，不提交
pnpm install --frozen-lockfile
pnpm build
```

如果安装会改 lockfile，先 `git diff --exit-code pnpm-lock.yaml` 检查；有改动就还原，不要带走。

### 4.3 把教程脚本移植到公司

优先移植“无侵入”的：

- `size-report.mjs`：只读 `dist`；
- `smoke.test.mjs`：只读产物；
- `bench.mjs`：只跑命令并记录；
- `deploy.sh`：先在公司测试环境用，不碰生产。

不要移植：

- 需要公司 secret 的 workflow；
- 会改分支保护的脚本；
- 会清理生产镜像/容器的命令。

## 5. 一页提案怎么写

```md
# 前端构建与发布改进提案（草案）

## 现状
- build 中位数：X 秒（命令：...，3 次）
- CI 中位数：X 分钟
- 最近 3 次发布问题：...
- 回滚方式：...（耗时 X 分钟）

## 问题
- 哪个问题最影响交付/稳定性？
- 发生在 PR、合并还是发布后？

## 建议（本轮只做一件事）
- 在 MR 增加非阻塞 build/smoke 检查
- 不改变现有发布流程
- 两周后复盘误报率与耗时

## 成本
- 配置：X 人日
- CI 增加：X 分钟/次
- 维护：谁负责

## 风险与回滚
- 误报：allow_failure，不挡合并
- 失败：删除 job 即恢复
- 不影响生产

## 需要谁支持
- CI 配置权限：...
- 测试环境：...
- 评审：...
```

一页就够。不要写“提升研发效能 30%”这种没有基线的话。

## 6. 常见反对意见与回应

| 反对 | 回应 |
|---|---|
| “我们没时间” | 本轮只加旁路 job，不挡发布；先跑两周看数据 |
| “老项目一跑就红” | 先只检查改动文件/新代码，或 allow_failure |
| “CI 会更慢” | 先测耗时；缓存/并行再优化；不达标就不 required |
| “出问题谁负责” | 旁路不影响发布；有明确回滚（删 job） |
| “GitLab 和教程不一样” | 附录 F 有可运行对照；概念一一映射 |
| “为什么不用 Turborepo/Nx” | 当前包数量和构建时长没到信号；先解决门禁/发布 |
| “直接上 K8s 吧” | 单机 Compose 够用；没有平台团队会增加故障面 |
| “先把 pnpm 换了吧” | 换包管理器是独立项目；先统一锁文件与 CI |

## 7. 公司版与个人版的差异

| 项 | 个人教程 | 公司落地 |
|---|---|---|
| CI | GitHub Actions | GitLab CI（附录 F） |
| Registry | GHCR | GitLab Container Registry |
| 部署 | 自家 QNAP 手动 | 测试环境/发布窗口，可能由运维执行 |
| 权限 | 自己全权 | 分支保护/变量/runner 由平台管 |
| 失败成本 | 自己的站点 | 团队/用户，必须先回滚 |
| 节奏 | 12 周连续 | 30/60/90 天，按发布窗口 |

## 8. 复盘指标

不要用“感觉快了”。至少记录：

- `install/build` 中位数；
- CI 总时长与排队时间；
- 检查误报率（失败但实际无问题）；
- 发布失败次数；
- 回滚耗时（MTTR）；
- 维护成本（每周花多少时间）。

数据放公司允许的位置；不要把内部数据发到个人仓库。

## 9. 最后的建议

- 先做一个**别人能感知**的小改进（少一次旧版发布、快 1 分钟构建）；
- 再谈架构；
- 每次只改一个变量；
- 任何门禁先旁路，稳定后再 required；
- 任何部署先有回滚；
- 不要用“最佳实践”压人，用你自己的基线数据说话。

> 公司落地不是把教程复制进公司，而是把教程里的**判断方法**带进去。
